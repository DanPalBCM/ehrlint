# LK009 — `duplicate_subjects`

**Subjects that look like the same person under two ids.**

| | |
| --- | --- |
| default severity | `warning` |
| injector | `ehrlint.inject.inject_lk009` |

## Why this matters

Patients get duplicate records across registrations, sites, and merges. Two ids for one person defeat a subject-level split in exactly the way LK005 guards against, but invisibly -- the split is disjoint by id while not being disjoint by person.

## What it looks like in practice

A patient registered twice -- at two sites, or before and after a record merge. The split is disjoint by id while not being disjoint by person, so LK005 is clean and the leak is invisible.

## A note on severity

Deterministic, not probabilistic, and it **skips** rather than guessing when the demographics in your data distinguish too few profiles for a collision to be evidence. Reporting arithmetic as a finding would be the fabricated statistic this project forbids.

## The query it runs

```sql
WITH sig AS (
  SELECT subject_id, STRING_AGG(DISTINCT code, '|' ORDER BY code) AS signature
  FROM events WHERE time IS NULL GROUP BY subject_id
)
SELECT signature, COUNT(DISTINCT subject_id) AS n_subject_ids
FROM sig GROUP BY signature HAVING n_subject_ids > 1
```

## What to do about it

Resolve the duplicates before splitting. A shared signature is a candidate for review, not a confirmed duplicate: twins and sparse demographics both produce collisions.
